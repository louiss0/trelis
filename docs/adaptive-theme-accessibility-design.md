# Adaptive themes and accessible component presentation

**Status:** Agreed design direction under review. Partial prototype code exists but is not a stable API or a complete implementation. Exact APIs, symbols, palette values, and implementation phases remain to be determined.

## Goals

Make component states visually concise, give every structural theme a coherent adaptive default palette, and provide a usable linear presentation for screen-reader users. Examples should be considered when implementation scope and rollout are planned; they do not define the default palettes merely by virtue of their current colors.

## Component states

- In normal presentation, use state symbols and theme-specific highlights in place of routine textual state markers.
- Communicate simultaneous states with separate, composable indicators. For choice rows, use `→` as the Unicode focus marker (`>` in ASCII), plus a restrained theme-specific highlight. For multi-selection, show checked/unchecked independently using `✓` / `○` in Unicode and `x` / `-` in ASCII, so focus and checked state can both be visible.
- For single-selection, offer five built-in selected/unselected symbol styles: filled/open circles (`●` / `○`, the default), squares (`■` / `□`), triangles (`▲` / `△`), dots-in-circles (`◉` / `○`), and checkmarks (`✓` / `○`). Proposed distinct ASCII selected/unselected pairs are `(*)` / `( )` for circles, `[x]` / `[ ]` for squares, `<^>` / `< >` for triangles, `(o)` / `(.)` for dots-in-circles, and `x` / `-` for checkmarks. Validate these pairs visually and with narrow layouts before finalizing. The application chooses one style for its prompts and can expose the setting to users; separate applications or sessions may choose independently, with no per-prompt override. These markers indicate actual selection, not merely focus or an unaccepted default.
- Mark a default choice independently from focus and selection using Unicode `★` or ASCII `D` in a dedicated position; screen-reader presentation uses a textual label. A default marker must not imply that the choice is already selected.
- For trees, use disclosure markers `▾` / `▸` for expanded / collapsed in Unicode and `v` / `>` in ASCII. Keep disclosure and focus positions distinct, and leave the disclosure position blank but aligned for leaves.
- Success, warning, and error messages include a clear textual status label alongside their symbols and optional semantic colors. Use Unicode `✓` / `!` / `×` for success / warning / error, with ASCII `+` / `!` / `x` respectively.
- All symbols remain subject to rendering and accessibility validation.
- Preserve consistent state meanings across themes, while allowing compatible symbol variants and distinct styling.
- Provide distinct ASCII alternatives when Unicode is unsuitable. State distinctions must remain usable without color.
- Mark locked choices with `[L]` and unavailable choices with `[!]` in both Unicode and ASCII presentations. Keep their specific explanatory reasons as readable text; do not rely on color or dimming. Allow users to focus these choices to inspect them, but do not allow selection or acceptance; make reasons visible or announced in linear presentation.
- Do not assume screen readers will speak a symbol or convey its intended meaning.

## Help and screen-reader presentation

Interactive prompts in normal presentation always include a concise help hint with the current stage's primary action and a route to detailed help. Noninteractive feedback does not display an artificial hint; show guidance there only when an actual user action exists. In rich interaction, keep it at the bottom of the active prompt area; in normal linear output, place it after content. Existing explicit hidden-instruction settings no longer suppress this essential hint; document that observable behavior change and migration. Retain an application option for expanded opening instructions in addition to the compact hint. When space is constrained, reduce decoration and shorten the hint before hiding essential content; keep a usable help route visible whenever space permits.

Detailed help is transient in capable rich terminals and otherwise appears in a readable transcript. Preserve draft, focus, and caret. In screen-reader presentation help remains sequential and text-based. Help routes are component-safe: do not reinterpret literal secrets or steal a key intended for capture; identify the applicable route in essential guidance.

Provide a screen-reader mode with textual state labels, linear interaction, and minimal in-place redraws. Before each prompt, show concise, context-specific essential instructions and a route to full help. Preserve component operations where practical, adapting controls to linear interaction when needed.

Use best-effort detection only as a hint: an affirmative signal may select screen-reader mode automatically; a negative or unknown result leaves the normal mode selected. Explicit on/off configuration takes precedence. Initially target the documented Windows screen-reader parameter and macOS VoiceOver-specific state, subject to verified native bindings; Linux remains unknown until a suitable signal is established. Enable each platform's native hint by default only after native binding tests and an actual screen-reader check on that platform. Windows Narrator does not set the documented parameter; document this limitation. Unsupported platforms and failed native screen-reader queries remain unknown and do not block the prompt. Allow applications to supply automatic hints as well. In automatic preference, any affirmative application or eligible native hint can enable screen-reader presentation; negative or unknown hints do not veto an affirmative hint. Explicit on/off still wins. A local OS signal may select screen-reader presentation only when the terminal session is reasonably known to be local; detected-remote or ambiguous sessions treat it as unknown. Use a conservative locality heuristic requiring an interactive terminal. Treat non-empty OpenSSH session indicators, recognized tmux or GNU screen context, a positive Windows Remote Desktop session observation, and a positively identified container as ambiguous. A failure in a required supported native locality check is also ambiguous. Do not launch subprocesses for container detection; use documented, safely accessible signals where available. An unavailable container check alone is not a veto, though positive evidence is ambiguous. Absence of these indicators is not proof of locality, so document possible false positives and validate the exact indicators, container-detection approach, and supported native signals before rollout. Collect automatic screen-reader detection once per theme-managed active period: a period begins when work acquires the shared resources and ends when the last active component finishes and cleanup completes. A later active period may detect again. Screen-reader preference and interaction mode are theme-wide and cannot be overridden by individual components; do not change an active prompt's interaction mid-invocation. Detection is not reliable across platforms, terminals, SSH, containers, or multiplexers, so users must not depend on successful detection to enable the mode. Applications should be able to expose these controls to their users.

For linear text entry, retain the existing documented backslash escape for literal command-shaped values, such as `\/cancel`. In every applicable linear prompt that retains a draft, preserve the literal meaning of identified pasted or escaped command-shaped text across invalid submissions and retries. Help and cancellation commands remain available regardless of the field's value length limit; enforce that limit on submitted values. Reject recognized multiline paste into a single-line field with a clear explanation, preserving the existing draft. Report the draft and cursor state on demand or when needed rather than after every edit; never expose secret values.

Suitable interactive linear prompts should request bracketed-paste reporting as a general input-safety measure, with capability checks and safe cleanup. Terminal support varies, and unframed paste cannot reliably be distinguished from typing. Validate native behavior; scripted tests alone are insufficient.

## Default palettes

- Each structural theme has its own default light- and dark-background palettes and may use a different color harmony. The defaults should feel like one family with distinct accent personalities and restrained neutrals, not unrelated products. The chosen starting direction is the prototype's Atelier / warm-ink family; individual accents and light/dark colors still need refinement, and the prototype does not establish final values.
- Reuse a small coordinated accent family across structures rather than requiring a unique primary accent for each. Chosen primary accent directions are ink blue for Rail, ASCII, Double, Chevron, and Colon; rust for Box, Bracket, and Block; plum for Branch, Round, and Line; and sepia for Minimal, Plain, Form, and Ledger. The mapping was retained after reviewing the complete-family visual prototype. Distinct light/dark shades remain to be refined; these are accent directions, not final color values.
- Blue is a recurring accent where it fits, not a requirement for every theme. Use electric blue selectively in focal areas, balanced by quieter text and borders. Neon blue is welcome where readable; legibility takes priority over a particular shade.
- Keep success, warning, and error in consistent semantic color families across themes, while adapting individual shades for the variant and contrast.
- Preserve the terminal background by default rather than painting the terminal surface; localized backgrounds such as selection highlights are allowed. For the Atelier direction, keep the prototype's dark-variant balance as a starting point and use Atelier Sepia as the starting direction for the light variant: warmer ink, borders, and supporting accents rather than relying on a painted surface. The prototype colors are not final. Contrast checks against reference backgrounds cannot guarantee contrast against an actual user's terminal background.
- Maintain coherent semantic roles for foreground, focus/selection, success, warning, error, and other applicable states.
- For authored normal-text foreground/background pairs with known RGB values, target a contrast ratio of at least 4.5:1 in both variants. This is a design and test target, not a guarantee about actual terminal rendering, custom colors, indexed palettes, or transparency.

## Automatic adaptation and overrides

Automatic behavior is the default. Adapt to available color capability and choose light or dark palettes from the background when it can be detected. In automatic mode, prefer a valid terminal query response over a passive hint; fall back to the dark-background variant if neither is available. Explicit light/dark selection takes precedence.

A background query is permitted only in suitable interactive sessions when querying is enabled and effective color output is available. Skip active querying when `NO_COLOR` applies or effective color depth is none. Use a fixed, library-selected timeout; preserve unrelated user input and fall back safely when unsupported. Allow applications to disable querying. Attempt detection once per theme-managed active period, caching the result while work remains active; a later active period may detect again. Coordinate queries with the existing input owner rather than adding a competing reader.

Keep the existing non-empty `NO_COLOR` restriction as a hard prohibition on color. States must remain distinguishable without it. Color capability, background choice, and screen-reader mode are distinct decisions; explicit configuration overrides automatic detection except for the `NO_COLOR` restriction.

Expose immutable color preferences for applications to connect to their own user-facing settings. A theme-level color preference composes a reusable component-color override value with background selection and active-query control; it does not inherit from the component type. The component override contains shared, light, and dark groups; each group can specify a whole palette and/or individual semantic roles. Component overrides cannot set background selection or query control; the theme owns detection. A component method has one typed color-override parameter, with a convenient named constructor for replacing a whole palette; exact names remain open. Omission inherits application-level settings; there is no dedicated reset-to-theme operation. Exact type and argument names remain open.

## Phase 1: configuration and compatibility contract

The first implementation phase establishes deterministic, injectable resolution before introducing native detection or changing component rendering.

- Keep output capability facts in `OutputProfile`. Provide separate interaction and grouped color preference types; resolve screen-reader, background, palette, and interaction mode independently. Automatic background selection falls back to dark when the background is unknown.
- Provide immutable typed application interaction preferences containing rich/linear mode (using the existing `PromptMode` direction), screen-reader preference, and an optional positive-only application hint. Omission defaults mode and screen-reader preference to automatic. These are configured for the theme, not passed to `.prompt()` or overridden by components. Exact names and signatures remain open. An internal state machine resolves interaction decisions; its transitions and general-purpose resolver are not public API.
- Model a successful effective interaction as rich/linear mode plus a separate screen-reader flag. Validate the invariant that screen-reader-active requires linear before rendering. Resolve interaction for the theme-managed session; editing, help, and resize are separate runtime events. Unavailable interaction and configuration conflicts are separate resolution outcomes, not runnable interaction states.
- Expose an immutable read-only runtime interaction value after resolution, limited to effective rich/linear mode and screen-reader presentation, without exposing the internal state-machine type. Configure the resolution callback on the theme rather than on `.prompt()` or the component. Invoke it only after successful resolution of a runnable interaction, not for unavailable requests or early failures. If it throws, propagate the error and restore any acquired terminal resources. Exact property and callback signatures remain to be designed.
- Use two configuration levels: optional application preferences supplied as separate named interaction and color arguments to a theme instance, and permitted named overrides on the theme's component-creating methods. Do not require an enclosing application-preferences object. The theme accepts one named I/O environment abstraction, defaulting to normal terminal I/O and supporting scripted or custom environments; the environment declares or overrides the `OutputProfile` associated with its selected output. Applications do not supply or configure a session. Remove the existing `SuppliedAnswer` and `SuppliedTags` public paths and explain their migration to supported alternatives; scripted I/O is not necessarily behaviorally equivalent. If scripted input ends before a prompt is answered, return the existing `InputEnded` outcome. The caller owns externally supplied streams by default; automatic terminal/session cleanup does not close caller-owned streams unless the environment explicitly transfers ownership. Color and optional expanded-instruction presentation may be overridden per component; structural layout is fixed by the theme, and screen-reader preference, rich/linear mode, single-selection symbol style, and session/I/O configuration are theme-wide. Configure the single-selection symbol style as its own named theme argument, separate from interaction and color preferences. The essential compact help hint remains mandatory. Interactive components are reusable and `.prompt()` is parameterless. Feedback retains appropriate invocation methods such as `.present()` and `.start()` rather than being forced into `.prompt()`; I/O remains theme-owned. The same prompt component can run sequentially, but concurrent invocations of it are rejected; each run starts from its configured initial value rather than retaining a prior answer. Each theme automatically manages shared terminal resources while components are active and permits one active prompt alongside coordinated live feedback. A second concurrent prompt is rejected. The prompt releases its participation when it finishes; live feedback remains active until it is stopped, completed, or fails. Resources are restored and released automatically once the last active component finishes; there is no public theme `close`. A later invocation starts a new active period. Different theme instances may use the same terminal sequentially, but identifiable overlapping active terminal ownership is rejected clearly. Themes and components capture immutable preferences at creation. Exact argument names remain open.
- Screen-reader preference supports automatic, explicitly on, and explicitly off. An affirmative detection hint selects linear mode in automatic preference unless rich interaction was explicitly requested. Negative or unknown detection does not select screen-reader mode. Explicitly turning screen-reader mode off prevents automatic selection; it does not prohibit an independently requested linear interaction.
- Explicit screen-reader-on selects linear interaction. If it conflicts with an explicit rich-mode request, report a clear configuration error rather than silently ignoring either request. An explicit rich request remains the requested mode even when the output does not support rich interaction; the resolver does not guarantee usability, and integration must still run existing availability checks.
- When no palette is supplied, use the structural theme's selected light or dark adaptive default. An explicitly supplied palette, including terminal-native colors, replaces that default. A replacement may provide different light and dark values.
- Resolve color customization by scope: start with the selected theme-variant default; apply the app's selected whole-palette replacement if supplied, then its shared and selected-variant role overrides; apply a component whole-palette replacement if supplied, then the component's shared and selected-variant role overrides. A component whole-palette replacement replaces the complete effective app palette, including its role overrides. Within a scope, role overrides apply after the selected palette and variant roles win over shared roles. Finally enforce the existing hard non-empty `NO_COLOR` restriction. The prototype resolver predates this reviewed rule and must not be assumed to implement it.
- Changing the omitted-palette default for named structural themes from terminal-native colors is an intentional observable behavior change. Omission selects adaptive behavior; an explicitly supplied `ColorTheme`, including `ColorThemes.terminalDefault`, keeps its existing meaning subject to the override layers and `NO_COLOR`. Replace static theme factories with theme instances and provide a migration guide; do not maintain a second permanent static API.
- Themes are the public component-construction path. Remove or internalize direct component construction rather than maintaining a second public configuration and terminal-ownership API; include direct-constructor migration in the guide.
- Validate resolution with synthetic inputs, including conflicting explicit modes, positive/negative/unknown detection, explicit screen-reader-off, both background variants and unknown fallback, all palette layers, terminal-native palettes, color depth, and `NO_COLOR`. Native detection and visible rendering are later phases.

### Detailed design defaults for implementation

The following names are design defaults, subject to verification against Dart's API and the existing generators: `InteractionPreferences`, `ColorPreferences`, `ComponentColors`, `ResolvedInteraction`, `ScreenReaderPreference`, and a single theme I/O environment type. Theme constructors use optional named `interaction`, `colors`, `selectionStyle`, `io`, and resolution-callback arguments. A component method's `colors` accepts `ComponentColors`; its whole-palette named constructor is a convenience. `ColorPreferences` composes `ComponentColors` and adds background selection and query control. Preserve the existing `PromptMode` and `OutputProfile` concepts, but do not expose an internal state-machine resolver. Exact signatures should be finalized and compiled during implementation rather than implying these names already exist publicly.

Theme-managed terminal resources are acquired lazily for an active period and automatically restored and released when its last active component completes. A prompt completing does not stop independently active feedback; a spinner ends when stopped, completed, or failed. Cleanup is awaited as part of completing the last operation. Preserve any committed answer, EOF, or primary failure, and make cleanup failures observable without silently erasing the primary result. A new operation racing cleanup must not reuse a partially released owner; safely serialize cleanup and reacquisition. The I/O environment supplies a stable ownership identity when it can; native environments should identify the selected terminal where safely possible. Different wrappers that cannot be identified as the same physical terminal cannot be guaranteed to be detected as overlapping, and that limitation must be documented.

The first prompt or feedback operation uses a common asynchronous theme initialization path so ownership and any bounded detection complete before output. Feedback `.present()` and `.start()` retain their names but may need asynchronous signatures; the cutover must migrate callers. A theme-wide configuration conflict prevents both prompt and feedback output; a prompt whose explicitly requested rich interaction is unavailable returns `Unavailable`, while feedback reports a clear error rather than writing in an unsupported mode. Check component-specific prompt availability before publishing its first successful interaction resolution.

The optional theme resolution callback runs at most once per active period, after successful resolution for its first eligible prompt or feedback operation and before it renders. It is not invoked solely for an unavailable request or a failure before resolution. The theme exposes its read-only resolved value for the current active period only after the callback succeeds; it is unavailable again after cleanup. If the callback throws, propagate the failure after acquired resources are restored and do not publish the value; a later invocation may start a fresh active period. Components already sharing an active period do not repeat the callback. These are theme-level observations, not additional preference layers.

The current factories cannot distinguish omitted colors from an explicitly supplied terminal-default palette without an API change. Use the instance API and migration described in the [implementation plan](adaptive-theme-implementation-plan.md); the old static API is replaced, not retained permanently.

## Prototype and stability gates

The prototype resolver and combined preferences object, plus standalone TextInput and Select experiments, do not yet match the reviewed API direction. They have been removed from the package's public barrel and prompt signatures and remain available through unsupported internal experiment seams. Retain their tested behavior as design evidence while redesigning the public API. Assess editor and paste-safety fixes independently and retain those justified on their own merits.

Do not publish the interaction preference API as stable until all interactive prompt families support a consistent contract, shared sessions support it with coordinated live feedback, and automated tests plus actual screen-reader testing have been completed. Include the existing Windows Terminal + NVDA baseline and document untested platforms. The approved full interaction release plan also waits for both Windows and macOS native hints to be validated and enabled; lack of that platform evidence blocks full interaction qualification, not unrelated implementation. Scripted tests alone do not establish screen-reader usability. The separate color preference API has its own stability gate and can mature independently.

## Validation and open planning work

- Test composable states, ASCII and no-color output, help placement, linear interaction, and explicit overrides.
- Check known palette pairs against the contrast target and review rendering in representative light and dark terminals. Include actual screen-reader and terminal testing; no single contrast calculation or detection signal establishes accessibility.
- Test background-query timeouts and input preservation, including redirected output and remote or multiplexed sessions.
- Validate the chosen symbols and ASCII fallbacks, refine exact theme palette values and public signatures, and establish supported native detection signals and platform evidence. Update examples to demonstrate defaults and overrides; follow the chosen replacement-and-migration strategy and phased implementation plan.
