## What was built

- `lib/src/prompt_structure.dart`: the heading half of the structural
  vocabulary.
  - `HeadingGlyphs` with the heading prefix and suffix, the body indent, the
    hint marker, the live-row body marker and the declared casing rule, plus the
    measured cell width of each part.
  - `headingGlyphsFor(structure, {required ascii})` for the four lightweight
    structures and null for every other structure, so no existing class changes
    behavior. `usesStructureHeading` names the family and
    `usesStructureFraming` now covers prefix **or** enclosure **or** heading.
  - `frameHeadingLines` applies the decoration to already-wrapped heading lines:
    the first line takes the prefix, the last takes the suffix, wrapped
    continuation lines take the body indent, and `compact: true` simplifies the
    decoration to its marker instead of replacing the structure.
  - `structureHeadingText` applies the declared casing rule to heading text
    only; `structurePrefixCells` reports the body indent and
    `structureLivePrefix` reports the structure's atlas body marker (`› `, `> `,
    `❯ `, `» `).
- `lib/src/themes/minimal_theme.dart`, `ascii_theme.dart`, `chevron_theme.dart`,
  `bracket_theme.dart`: `MinimalTheme`, `AsciiTheme`, `ChevronTheme` and
  `BracketTheme` with all 38 typed static factories each, generated by
  `tool/generate_theme_factories.py` from `plain_theme.dart` and forwarding
  `structure:` with their own value. Exported from `lib/prompty.dart`.
  `tool/generate_theme_factories.py` now keeps the generated `structure:` line on
  its own row instead of joining it to the previous argument.
- `_StructureSpine` (internal, `lib/src/text_input.dart`) renders a third
  grammar through the same seam as the prefix and enclosure paths:
  - `heading()` decorates the stage heading. A structure without a heading
    grammar writes the block exactly as `write()` would, which is what keeps the
    plain, rail, branch, box, round and double bytes unchanged.
  - `write()` writes every later block as an indented body row, and `hint()`
    writes the compact hint under the body rows with the structure's hint
    marker (with a narrow-width simplification that keeps the marker rather than
    overflowing the columns).
  - `opening(title, body)` is the split used by components whose stage opening
    mixes a heading with state: the reference, rail, branch and enclosing
    presentations keep the exact single merged block they wrote before, and a
    heading structure separates the heading from its body rows.
  - Wrapping measures the heading decoration, the body indent and the hint
    marker as part of the declared width, and an over-narrow width simplifies
    the decoration to its marker instead of silently becoming PlainTheme.
- Heading rendering wired into every applicable interactive render path in rich

## Structure grammar check

`test/theme_heading_framing_test.dart` runs every applicable interactive
component (all 34) through each of the four structures in both interaction
modes, plus the four feedback components per structure (and both modes for the
three live ones), and asserts:

- the stage opens with the structure's own heading decoration: `? ` for the
  console grammar, `❯ ` for the chevron, `[ … ]` for the bracketed band, and the
  bare reference column for the conversational grammar;
- the console heading is spelled in capitals, and the bracket heading closes its
  band;
- every stage has body rows indented under the heading, and every line of the
  run keeps the declared vocabulary (heading prefix, body indent or the
  structure's own live-row marker) instead of falling back to the undecorated
  reference column;
- the bare grammar adds no marker anywhere and its heading starts at the
  reference column;
- no line of any run contains a framing glyph (`┌ ┐ └ ┘ ╭ ╮ ╰ ╯ ╔ ╗ ╚ ╝ │ ║ ├
  +- \-`): the four lightweight structures decorate, they never enclose;
- no line exceeds the declared columns, a 200-column profile still stays inside
  the 120-cell prompt width cap, and 24 columns keep every line inside 24;
- at 4 columns the decoration simplifies to its marker (`?`, `>`, `[`) and no
  line exceeds 4 cells, so the structure is never silently replaced;
- rich output uses the declared Unicode vocabulary and an `automatic` glyph
  profile falls back to the ASCII counterpart with no `❯`, `↳`, `»` or `›` in
  the output;
- the console grammar has exactly one vocabulary under every profile: the
  Unicode and ASCII lookups are the same object and every part is ASCII;
- a palette `foreground` styles the stage while the accepted value is unchanged;
- the compact hint keeps the structure's hint grammar and sits below the body
  rows; a literal `/Help` in validation text is never re-cased; a protected
  message keeps its `\u{0007}` spelling; a masked password is never echoed; an
  unavailable choice keeps its reason and a reported outcome keeps the body
  indent;
- stage help keeps the structure grammar;
- a rich focus move re-decorates the heading for every presentation, so each
  transcript stage keeps the grammar without repainting a frame;
- standalone feedback gains the structure's body marker without a frame for
  `Text`, `Progress`, `Spinner` and `MultiSpinner` in both modes;
- `TextInput`, `Select`, `Confirm` and `Password` produce the same outcome for
  `plain`, `minimal`, `ascii`, `chevron` and `bracket` in both modes, and the
  reference presentation still emits no heading chrome.

Separately, `test/theme_structure_rendering_test.dart` still pins linear
`TextInput` output byte-for-byte for `RailTheme`, `BranchTheme` and
`PlainTheme` at an `automatic` glyph profile and at a 72-column Unicode profile,
and `test/theme_enclosure_framing_test.dart` still runs its whole box, round and
double matrix; both pass unchanged (apart from the framing invariant that now
covers the heading family).

## Limitations and remaining work

- MinimalTheme is the unframed conversational grammar, so its stage content
  shares the reference column-0 layout: what distinguishes it in this revision
  is the declared absence of any decoration plus its own live-row marker `› `
  (`> ` under ASCII). It is a declared arrangement, not a re-skin of PlainTheme,
  and it never borrows a frame under a narrow width or a weak glyph profile —
  but a reader who expects a visibly different body column from PlainTheme will
  not find one.
- The console grammar's capitals apply to the stage heading a component owns.
  Components whose opening block used to mix a heading with state were split so
  retained input stays in body rows; `Confirm`/`Checkbox`/`Toggle` state
  (`Default: …`, `Draft: …`) and `DateInput` draft segments are body rows for the
  same reason. A heading that a component itself spells with a value would still
  be re-cased, which is why no component does that.
- A rich repaint redraws the decorated heading and its body rows for each
  presentation, the same way a rail repeats its spine and a frame redraws its
  rules. The compact hint is written once per stage for the choice families (as
  a rail does) and re-written per field stage for `DateInput`/`TimeInput`, so a
  navigation transcript shows the grammar more than once but never duplicates a
  hint inside one presentation.
- Heading structures do not draw the atlas's breathing row between a heading and
  a choice list: like the reference presentation and the rail, they keep the rows
  they already wrote, so a choice list is separated by the page cue only.
- The four structures render the body indent and the hint marker the atlas
  declares, but not the atlas's per-mode body glyphs (for example the numbered
  ASCII choices or the bracket focus cursor). Choice rows keep the shared
  numbered, focus-marked row, which every structure already had.
- `EmailInput`'s domain interpretation row keeps the heading grammar for the four
  lightweight structures only. The rail, branch and enclosure structures keep
  the raw row they wrote before, because changing it would change their
  already-published bytes.
- No native-terminal visual qualification was performed: every result here is
  scripted output, not a screenshot or a manual terminal review. Windows native
  and GUI probe evidence for the theming families remains a separate ticket.

## Conclusion

The `MinimalTheme`, `AsciiTheme`, `ChevronTheme` and `BracketTheme` factory
namespaces, the heading vocabulary and its composition helpers, and the four
heading grammars across every applicable interactive and feedback render path are
implemented, verified by 2488 passing tests, and committed. The plain, rail,
branch, box, round and double presentations keep their bytes, the ledger of
protected content and outcomes is unchanged, and the ticket is **resolved** with
the worktree ready for merger.
